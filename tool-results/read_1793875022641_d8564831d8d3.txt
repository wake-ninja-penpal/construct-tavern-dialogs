     1→     1→
     2→     2→# ТЗ: общий доступ, realtime-синхронизация, копии и merge для «Ветвей»
     3→     3→
     4→     4→## 1. Контекст
     5→     5→
     6→     6→Сейчас «Ветви» — это браузерный конструктор нарратива с локальной работой:
     7→     7→
     8→     8→- холст;
     9→     9→- элементы;
    10→    10→- инспектор;
    11→    11→- реплики диалога;
    12→    12→- заметки;
    13→    13→- автосохранение;
    14→    14→- экспорт/импорт JSON;
    15→    15→- экспорт в текстовый файл.
    16→    16→
    17→    17→Нужно добавить возможность:
    18→    18→
    19→    19→1. дать другому человеку ссылку на проект;
    20→    20→2. чтобы второй человек мог подключиться к проекту в realtime;
    21→    21→3. чтобы участники могли совместно редактировать проект, пока оба онлайн;
    22→    22→4. чтобы любой участник мог сделать копию проекта себе;
    23→    23→5. чтобы позже изменения из копии можно было отправить владельцу оригинала;
    24→    24→6. чтобы владелец оригинала мог просмотреть, принять или отклонить эти изменения.
    25→    25→
    26→    26→При этом важное ограничение:
    27→    27→
    28→    28→> Фронтенд должен хоститься на GitHub Pages.  
    29→    29→> Полноценный собственный backend делать не хочется.
    30→    30→
    31→    31→---
    32→    32→
    33→    33→## 2. Цель фичи
    34→    34→
    35→    35→Сделать минимальный совместный режим работы над проектом «Ветви» без полноценного бэкенда, используя:
    36→    36→
    37→    37→- статический фронтенд на GitHub Pages;
    38→    38→- Yjs как CRDT-модель совместного документа;
    39→    39→- WebRTC как транспорт для realtime-обмена изменениями;
    40→    40→- локальное хранение проекта у создателя через IndexedDB;
    41→    41→- механизм копий и merge-запросов.
    42→    42→
    43→    43→---
    44→    44→
    45→    45→## 3. Ключевой принцип
    46→    46→
    47→    47→> Проект хранится у создателя, но realtime-доступ возможен только тогда, когда создатель или другой участник с актуальной копией находится онлайн.
    48→    48→
    49→    49→Это важно зафиксировать, потому что в модели «только GitHub Pages + WebRTC» нет постоянного сервера хранения.
    50→    50→
    51→    51→То есть:
    52→    52→
    53→    53→- если создатель онлайн — проект доступен для подключения;
    54→    54→- если создатель офлайн, но кто-то из участников онлайн с актуальной копией — можно подключиться к нему;
    55→    55→- если все офлайн — проект живёт только локально у тех, кто его сохранял.
    56→    56→
    57→    57→Для MVP это приемлемо.
    58→    58→
    59→    59→---
    60→    60→
    61→    61→## 4. Пользовательские роли
    62→    62→
    63→    63→### 4.1. Создатель / владелец проекта
    64→    64→
    65→    65→Тот, кто создал проект.
    66→    66→
    67→    67→Возможности:
    68→    68→
    69→    69→- создавать проект;
    70→    70→- редактировать проект;
    71→    71→- открывать realtime-комнату;
    72→    72→- давать ссылку другим;
    73→    73→- хранить основную версию проекта локально;
    74→    74→- получать merge-запросы из копий;
    75→    75→- просматривать изменения перед применением;
    76→    76→- принимать или отклонять merge-запросы.
    77→    77→
    78→    78→### 4.2. Соавтор / участник
    79→    79→
    80→    80→Тот, кто открыл ссылку на проект.
    81→    81→
    82→    82→Возможности:
    83→    83→
    84→    84→- подключиться к realtime-комнате;
    85→    85→- видеть текущее состояние проекта;
    86→    86→- редактировать проект, пока подключён;
    87→    87→- сделать копию проекта себе;
    88→    88→- позже отправить изменения из копии владельцу оригинала.
    89→    89→
    90→    90→### 4.3. Редактор копии
    91→    91→
    92→    92→Тот, кто работает локально со своей копией.
    93→    93→
    94→    94→Возможности:
    95→    95→
    96→    96→- открыть свою копию;
    97→    97→- редактировать её без обязательного подключения к оригиналу;
    98→    98→- отправить merge-запрос, когда оригинал снова станет доступен.
    99→    99→
   100→   100→---
   101→   101→
   102→   102→## 5. Основные пользовательские сценарии
   103→   103→
   104→   104→### Сценарий 1. Создать проект и открыть доступ
   105→   105→
   106→   106→1. Пользователь открывает «Ветви».
   107→   107→2. Создаёт проект.
   108→   108→3. Добавляет элементы, реплики, заметки.
   109→   109→4. Проект автоматически сохраняется локально.
   110→   110→5. Пользователь нажимает «Поделиться».
   111→   111→6. Приложение генерирует ссылку вида:
   112→   112→
   113→   113→```text
   114→   114→https://username.github.io/vetvi/#room=...&project=...
   115→   115→```
   116→   116→
   117→   117→7. Пользователь отправляет ссылку другому человеку.
   118→   118→
   119→   119→---
   120→   120→
   121→   121→### Сценарий 2. Подключиться по ссылке и работать вместе
   122→   122→
   123→   123→1. Второй пользователь открывает ссылку.
   124→   124→2. Приложение подключается к WebRTC-комнате.
   125→   125→3. Если создатель онлайн, второй пользователь получает текущее состояние проекта.
   126→   126→4. Оба видят количество участников.
   127→   127→5. Изменения одного участника появляются у другого в realtime.
   128→   128→
   129→   129→Пример:
   130→   130→
   131→   131→- создатель двигает элемент;
   132→   132→- соавтор видит движение;
   133→   133→- соавтор меняет текст;
   134→   134→- создатель видит изменение текста.
   135→   135→
   136→   136→---
   137→   137→
   138→   138→### Сценарий 3. Сделать копию проекта
   139→   139→
   140→   140→1. Участник находится в проекте.
   141→   141→2. Нажимает «Сделать копию».
   142→   142→3. Приложение сохраняет локальную копию проекта.
   143→   143→4. Запоминается:
   144→   144→   - идентификатор копии;
   145→   145→   - идентификатор оригинала;
   146→   146→   - комната оригинала;
   147→   147→   - состояние оригинала на момент копирования;
   148→   148→   - дата создания.
   149→   149→5. Копия появляется в списке локальных копий.
   150→   150→
   151→   151→---
   152→   152→
   153→   153→### Сценарий 4. Работать в копии офлайн
   154→   154→
   155→   155→1. Пользователь открывает свою копию.
   156→   156→2. Приложение переходит в режим «копия».
   157→   157→3. Пользователь редактирует копию локально.
   158→   158→4. Изменения сохраняются в IndexedDB.
   159→   159→5. Оригинал при этом может быть офлайн.
   160→   160→
   161→   161→---
   162→   162→
   163→   163→### Сценарий 5. Отправить изменения из копии в оригинал
   164→   164→
   165→   165→1. Пользователь находится в копии.
   166→   166→2. Нажимает «Отправить merge».
   167→   167→3. Приложение вычисляет разницу между копией и состоянием оригинала на момент копирования.
   168→   168→4. Приложение подключается к служебной merge-комнате оригинала.
   169→   169→5. Отправляет merge-запрос.
   170→   170→6. Если владелец оригинала онлайн, он получает запрос.
   171→   171→7. Если владелец офлайн, запрос может остаться в локальной очереди отправителя до следующей попытки.
   172→   172→
   173→   173→---
   174→   174→
   175→   175→### Сценарий 6. Принять изменения в оригинале
   176→   176→
   177→   177→1. Владелец оригинала открывает проект.
   178→   178→2. Подключается к merge-комнате.
   179→   179→3. Видит входящие merge-запросы.
   180→   180→4. Для каждого запроса видит краткую сводку:
   181→   181→   - кто отправил;
   182→   182→   - когда;
   183→   183→   - сколько элементов добавлено;
   184→   184→   - сколько изменено;
   185→   185→   - сколько удалено.
   186→   186→5. Владелец может:
   187→   187→   - принять;
   188→   188→   - отклонить.
   189→   189→6. При принятии изменения применяются к оригиналу.
   190→   190→7. Перед применением создается локальный backup состояния оригинала.
   191→   191→
   192→   192→---
   193→   193→
   194→   194→## 6. Функциональные требования
   195→   195→
   196→   196→### FR-1. Идентификация проекта и комнаты
   197→   197→
   198→   198→Система должна поддерживать:
   199→   199→
   200→   200→- уникальный `projectId`;
   201→   201→- уникальный `roomId` для realtime-комнаты;
   202→   202→- ссылку формата:
   203→   203→
   204→   204→```text
   205→   205→#room=...&project=...
   206→   206→```
   207→   207→
   208→   208→Требования:
   209→   209→
   210→   210→- `projectId` не должен меняться при обычном редактировании;
   211→   211→- `roomId` должен быть случайным и достаточно длинным, чтобы ссылку нельзя было легко угадать;
   212→   212→- ссылка должна работать на GitHub Pages без серверных rewrite-правил;
   213→   213→- параметры должны находиться в hash-части URL, чтобы не зависеть от маршрутизации сервера.
   214→   214→
   215→   215→---
   216→   216→
   217→   217→### FR-2. Realtime-подключение по ссылке
   218→   218→
   219→   219→Приложение должно:
   220→   220→
   221→   221→- читать `roomId` из URL;
   222→   222→- подключаться к WebRTC-комнате;
   223→   223→- показывать статус подключения:
   224→   224→  - офлайн;
   225→   225→  - подключение;
   226→   226→  - подключено;
   227→   227→  - ошибка;
   228→   228→- показывать количество участников;
   229→   229→- автоматически переподключаться при временном разрыве, насколько это возможно.
   230→   230→
   231→   231→Важно:
   232→   232→
   233→   233→> Для WebRTC нужен signaling-канал.  
   234→   234→> В MVP допускается использовать публичный signaling-сервис.  
   235→   235→> Для продакшена позже желательно поднять свой мини-signaling.
   236→   236→
   237→   237→---
   238→   238→
   239→   239→### FR-3. Синхронизация состояния проекта
   240→   240→
   241→   241→В realtime-режиме должны синхронизироваться как минимум:
   242→   242→
   243→   243→- элементы на холсте;
   244→   244→- их позиция;
   245→   245→- их размер;
   246→   246→- их тип;
   247→   247→- их текст;
   248→   248→- связи между элементами, если они есть в текущей модели;
   249→   249→- реплики диалога;
   250→   250→- заметки;
   251→   251→- метаинформация проекта:
   252→   252→  - название;
   253→   253→  - версия схемы;
   254→   254→  - дата создания;
   255→   255→  - дата изменения.
   256→   256→
   257→   257→Не обязательно в MVP синхронизировать:
   258→   258→
   259→   259→- локальное выделение пользователя;
   260→   260→- состояние скролла;
   261→   261→- zoom;
   262→   262→- открытые модалки;
   263→   263→- черновые состояния UI.
   264→   264→
   265→   265→Но можно добавить позже.
   266→   266→
   267→   267→---
   268→   268→
   269→   269→### FR-4. Локальное хранение у создателя
   270→   270→
   271→   271→Создатель проекта должен хранить основную версию проекта локально.
   272→   272→
   273→   273→Требования:
   274→   274→
   275→   275→- проект сохраняется в IndexedDB;
   276→   276→- автосохранение должно продолжаться работать;
   277→   277→- после перезагрузки страницы проект восстанавливается;
   278→   278→- экспорт в JSON должен оставаться возможным;
   279→   279→- импорт из JSON должен оставаться возможным.
   280→   280→
   281→   281→Важно:
   282→   282→
   283→   283→> В P2P-модели любой подключившийся участник технически получает копию документа в память браузера.  
   284→   284→> Нельзя гарантировать, что гость не сохранит или не скопирует данные.  
   285→   285→> Поэтому «хранение у создателя» означает каноническую локальную версию, а не абсолютную защиту от копирования.
   286→   286→
   287→   287→---
   288→   288→
   289→   289→### FR-5. Создание копии проекта
   290→   290→
   291→   291→Любой участник должен иметь возможность создать копию текущего проекта.
   292→   292→
   293→   293→Копия должна содержать:
   294→   294→
   295→   295→- собственный `copyId`;
   296→   296→- снимок состояния проекта на момент копирования;
   297→   297→- ссылку на исходный проект;
   298→   298→- ссылку на исходную комнату;
   299→   299→- базовое состояние оригинала для будущего merge;
   300→   300→- дату создания.
   301→   301→
   302→   302→Копия должна сохраняться локально в IndexedDB.
   303→   303→
   304→   304→---
   305→   305→
   306→   306→### FR-6. Работа с копией
   307→   307→
   308→   308→Пользователь должен иметь возможность:
   309→   309→
   310→   310→- открыть список своих копий;
   311→   311→- открыть копию;
   312→   312→- редактировать копию локально;
   313→   313→- видеть, что сейчас активен режим «копия», а не «оригинал»;
   314→   314→- вернуться к оригиналу или другому проекту.
   315→   315→
   316→   316→---
   317→   317→
   318→   318→### FR-7. Вычисление изменений копии
   319→   319→
   320→   320→Приложение должно уметь вычислить, что именно изменилось в копии относительно момента её создания.
   321→   321→
   322→   322→Концептуально это означает:
   323→   323→
   324→   324→- есть оригинал в состоянии `A`;
   325→   325→- из него создана копия;
   326→   326→- копия изменена до состояния `B`;
   327→   327→- нужно получить дельту `B - A`;
   328→   328→- эту дельту можно применить к оригиналу.
   329→   329→
   330→   330→В Yjs это реализуется через механизмы состояния документа и state vector, но в ТЗ достаточно зафиксировать поведение.
   331→   331→
   332→   332→---
   333→   333→
   334→   334→### FR-8. Merge-запросы
   335→   335→
   336→   336→Изменения из копии не должны автоматически применяться к оригиналу.
   337→   337→
   338→   338→Нужен механизм merge-запросов.
   339→   339→
   340→   340→Merge-запрос должен содержать:
   341→   341→
   342→   342→- идентификатор запроса;
   343→   343→- идентификатор отправителя;
   344→   344→- имя или метку отправителя;
   345→   345→- идентификатор копии;
   346→   346→- идентификатор исходной комнаты;
   347→   347→- дату создания;
   348→   348→- дельту изменений;
   349→   349→- статус:
   350→   350→  - pending;
   351→   351→  - applied;
   352→   352→  - rejected.
   353→   353→
   354→   354→---
   355→   355→
   356→   356→### FR-9. Почтовый ящик оригинала
   357→   357→
   358→   358→Для merge-запросов нужна отдельная служебная комната, условно «mailbox».
   359→   359→
   360→   360→Например:
   361→   361→
   362→   362→- основная комната проекта: `roomId`
   363→   363→- merge-комната: `roomId + mailbox suffix`
   364→   364→
   365→   365→Требования:
   366→   366→
   367→   367→- merge-комната не должна смешиваться с основным документом проекта;
   368→   368→- в неё можно отправлять заявки;
   369→   369→- владелец оригинала может подключиться к ней и получить заявки;
   370→   370→- заявки должны быть видны только в контексте конкретного оригинала.
   371→   371→
   372→   372→---
   373→   373→
   374→   374→### FR-10. Просмотр merge-запроса владельцем
   375→   375→
   376→   376→Владелец оригинала должен видеть список входящих запросов.
   377→   377→
   378→   378→Для каждого запроса нужно показывать:
   379→   379→
   380→   380→- автора;
   381→   381→- дату;
   382→   382→- статус;
   383→   383→- краткую статистику изменений;
   384→   384→- кнопки «Принять» и «Отклонить».
   385→   385→
   386→   386→Минимальная статистика:
   387→   387→
   388→   388→- добавлено элементов;
   389→   389→- изменено элементов;
   390→   390→- удалено элементов;
   391→   391→- изменено реплик;
   392→   392→- изменено заметок;
   393→   393→- изменено связей, если applicable.
   394→   394→
   395→   395→Для MVP достаточно сводки. Подробный visual diff можно отложить.
   396→   396→
   397→   397→---
   398→   398→
   399→   399→### FR-11. Применение merge-запроса
   400→   400→
   401→   401→При нажатии «Принять»:
   402→   402→
   403→   403→1. система создает backup текущего состояния оригинала;
   404→   404→2. применяет дельту к оригиналу;
   405→   405→3. помечает запрос как `applied`;
   406→   406→4. обновляет UI;
   407→   407→5. показывает уведомление об успехе.
   408→   408→
   409→   409→При нажатии «Отклонить»:
   410→   410→
   411→   411→1. запрос помечается как `rejected`;
   412→   412→2. оригинал не изменяется.
   413→   413→
   414→   414→---
   415→   415→
   416→   416→### FR-12. Обработка ошибок
   417→   417→
   418→   418→Приложение должно показывать понятные ошибки, а не падать молча.
   419→   419→
   420→   420→Минимум:
   421→   421→
   422→   422→- не удалось подключиться к signaling;
   423→   423→- WebRTC не запустился;
   424→   424→- не удалось создать копию;
   425→   425→- не удалось отправить merge-запрос;
   426→   426→- merge-запрос не найден;
   427→   427→- запрос не относится к текущей комнате;
   428→   428→- ошибка чтения/записи IndexedDB;
   429→   429→- ошибка импорта/экспорта JSON.
   430→   430→
   431→   431→---
   432→   432→
   433→   433→### FR-13. Совместимость с текущим экспортом/импортом
   434→   434→
   435→   435→Текущие функции должны сохраниться:
   436→   436→
   437→   437→- Сохранить;
   438→   438→- Открыть;
   439→   439→- Сохранить JSON;
   440→   440→- Сохранить как JSON;
   441→   441→- Текстовый файл.
   442→   442→
   443→   443→Новый формат проекта должен быть совместим или иметь версию схемы.
   444→   444→
   445→   445→Рекомендуется добавить:
   446→   446→
   447→   447→```text
   448→   448→format: vetvi-project
   449→   449→schemaVersion: 1
   450→   450→```
   451→   451→
   452→   452→Если текущий JSON уже имеет другую структуру, нужен миграционный слой.

   456→   456→## 7. Нефункциональные требования
   457→   457→
   458→   458→### NF-1. Хостинг
   459→   459→
   460→   460→Приложение должно оставаться статическим и хоститься на GitHub Pages.
   461→   461→
   462→   462→Разрешено использовать:
   463→   463→
   464→   464→- внешние CDN для JS-библиотек;
   465→   465→- публичные signaling-сервисы для WebRTC;
   466→   466→- локальное хранилище браузера.
   467→   467→
   468→   468→Не требуется в MVP:
   469→   469→
   470→   470→- собственный API;
   471→   471→- база данных на сервере;
   472→   472→- авторизация;
   473→   473→- серверная бизнес-логика.
   474→   474→
   475→   475→---
   476→   476→
   477→   477→### NF-2. Производительность
   478→   478→
   479→   479→Синхронизация не должна подвисать UI при обычном количестве элементов.
   480→   480→
   481→   481→Ожидаемый масштаб MVP:
   482→   482→
   483→   483→- десятки элементов;
   484→   484→- сотни текстовых полей;
   485→   485→- несколько участников одновременно.
   486→   486→
   487→   487→Не требуется оптимизировать под тысячи узлов и десятки пользователей сразу.
   488→   488→
   489→   489→---
   490→   490→
   491→   491→### NF-3. Надежность
   492→   492→
   493→   493→Нужны:
   494→   494→
   495→   495→- reconnect;
   496→   496→- локальное сохранение;
   497→   497→- backup перед merge;
   498→   498→- очередь неотправленных merge-запросов;
   499→   499→- graceful degradation, если WebRTC недоступен.
   500→   500→
   501→   501→Если realtime недоступен, пользователь должен иметь возможность:
   502→   502→
   503→   503→- работать локально;
   504→   504→- экспортировать JSON;
   505→   505→- позже импортировать или отправить merge.
   506→   506→
   507→   507→---
   508→   508→
   509→   509→### NF-4. Безопасность и приватность
   510→   510→
   511→   511→Для MVP:
   512→   512→
   513→   513→- ссылка на комнату считается секретом;
   514→   514→- кто имеет ссылку, тот может подключиться;
   515→   515→- данные передаются между браузерами через WebRTC;
   516→   516→- signaling видит идентификатор комнаты, но не обязан видеть содержимое проекта;
   517→   517→- клиентские ограничения не являются настоящей защитой от злонамеренного участника.
   518→   518→
   519→   519→Не входит в MVP:
   520→   520→
   521→   521→- серверная авторизация;
   522→   522→- роли с криптографической проверкой;
   523→   523→- защита от экспорта данных участником;
   524→   524→- end-to-end шифрование с паролями.
   525→   525→

   528→   528→## 8. Ограничения подхода
   529→   529→
   530→   530→Важно честно зафиксировать ограничения.
   531→   531→
   532→   532→### 8.1. GitHub Pages не может быть signaling-сервером
   533→   533→
   534→   534→GitHub Pages отдаёт только статику.
   535→   535→
   536→   536→Он не может:
   537→   537→
   538→   538→- принимать WebSocket-соединения;
   539→   539→- хранить realtime-комнаты;
   540→   540→- обрабатывать серверную логику.
   541→   541→
   542→   542→Поэтому для realtime нужен внешний посредник:
   543→   543→
   544→   544→- публичный signaling для WebRTC;
   545→   545→- или свой мини-signaling;
   546→   546→- или managed realtime-сервис.
   547→   547→
   548→   548→---
   549→   549→
   550→   550→### 8.2. WebRTC может не сработать в сложных сетях
   551→   551→
   552→   552→Без TURN-сервера часть пользователей может не соединиться.
   553→   553→
   554→   554→Проблемные случаи:
   555→   555→
   556→   556→- корпоративные файрволы;
   557→   557→- строгие NAT;
   558→   558→- мобильные сети;
   559→   559→- CGNAT;
   560→   560→- VPN;
   561→   561→- блокировка UDP.
   562→   562→
   563→   563→Для MVP это допустимо.  
   564→   564→Для продакшена нужен TURN или fallback на WebSocket relay.
   565→   565→
   566→   566→---
   567→   567→
   568→   568→### 8.3. Если владелец офлайн, проект не «живёт в облаке»
   569→   569→
   570→   570→В модели «данные у создателя» нет постоянного серверного хранения.
   571→   571→
   572→   572→Если все закрыли вкладки:
   573→   573→
   574→   574→- проект существует только локально у тех, кто его сохранял;
   575→   575→- новый участник не сможет подключиться, если никто не держит комнату;
   576→   576→- merge-запросы могут не доставляться, пока стороны снова не окажутся онлайн.
   577→   577→
   578→   578→---
   579→   579→
   580→   580→### 8.4. Полный read-only без сервера обеспечить сложно
   581→   581→
   582→   582→Если участник подключился к документу, он технически может изменить свою локальную копию.
   583→   583→
   584→   584→Можно сделать:
   585→   585→
   586→   586→- UI read-only;
   587→   587→- запрет редактирования в интерфейсе.
   588→   588→
   589→   589→Но нельзя гарантировать, что человек с DevTools не обойдёт ограничение.
   590→   590→
   591→   591→Для доверенных соавторов это нормально.  
   592→   592→Для строгой защиты нужен серверный контроль.
   593→   593→

   726→   726→## 11. Требования к ID и конфликтам
   727→   727→
   728→   728→### 11.1. Уникальные ID
   729→   729→
   730→   730→Все сущности должны иметь стабильные уникальные ID.
   731→   731→
   732→   732→Нельзя:
   733→   733→
   734→   734→- пересоздавать ID при каждом сохранении;
   735→   735→- использовать индекс массива как ID;
   736→   736→- переиспользовать удалённые ID.
   737→   737→
   738→   738→Рекомендуется:
   739→   739→
   740→   740→- UUID или аналог;
   741→   741→- ID создаётся один раз при создании сущности.
   742→   742→
   743→   743→### 11.2. Конфликты полей
   744→   744→
   745→   745→Для скалярных полей, например `x`, `y`, `width`, применяется CRDT-разрешение конфликта.
   746→   746→
   747→   747→Для текста лучше использовать коллаборативный текстовый тип, если нужно посимвольное слияние.
   748→   748→
   749→   749→Если текст хранится как обычная строка, то при одновременном изменении одного поля победит одно из значений по правилам CRDT.
   750→   750→
   751→   751→### 11.3. Удаление и изменение
   752→   752→
   753→   753→Если один участник удалил элемент, а другой его изменил, система должна предсказуемо разрешить конфликт.
   754→   754→
   755→   755→Для MVP достаточно положиться на Yjs.  
   756→   756→Для более зрелой версии можно добавить tombstones и UI конфликтов.

   876→   876→## 14. Требования к merge
   877→   877→
   878→   878→### 14.1. Merge не должен быть полностью автоматическим
   879→   879→
   880→   880→Владелец оригинала должен подтверждать применение изменений.
   881→   881→
   882→   882→Причина:
   883→   883→
   884→   884→- даже CRDT может привести к неочевидному результату;
   885→   885→- пользователь должен понимать, что принимает чужие правки.
   886→   886→
   887→   887→### 14.2. Нужен preview
   888→   888→
   889→   889→Минимальный preview:
   890→   890→
   891→   891→- сколько объектов добавлено;
   892→   892→- сколько изменено;
   893→   893→- сколько удалено.
   894→   894→
   895→   895→Желательно в будущем:
   896→   896→
   897→   897→- список изменённых элементов;
   898→   898→- подсветка на холсте;
   899→   899→- режим «посмотреть до применения».
   900→   900→
   901→   901→### 14.3. Нужен backup
   902→   902→
   903→   903→Перед применением merge нужно сохранить snapshot оригинала.
   904→   904→
   905→   905→Это позволит откатить состояние, если изменения оказались нежелательными.

   909→   909→## 15. Требования к signaling
   910→   910→
   911→   911→### 15.1. MVP

   999→   999→## 18. Критерии приёмки MVP
  1000→  1000→
  1001→  1001→### 18.1. Локальный проект
  1002→  1002→
  1003→  1003→- Пользователь создаёт проект.
  1004→  1004→- Добавляет элемент.
  1005→  1005→- Перезагружает страницу.
  1006→  1006→- Проект восстановлен.
  1007→  1007→
  1008→  1008→### 18.2. Поделиться
  1009→  1009→
  1010→  1010→- Пользователь нажимает «Поделиться».
  1011→  1011→- В URL появляются `room` и `project`.
  1012→  1012→- Ссылка копируется.
  1013→  1013→- Статус меняется на «подключение» или «подключено».
  1014→  1014→
  1015→  1015→### 18.3. Realtime
  1016→  1016→
  1017→  1017→- Второй браузер открывает ссылку.
  1018→  1018→- Оба пользователя видят один проект.
  1019→  1019→- Изменение элемента в одном браузере появляется в другом.
  1020→  1020→- Перемещение элемента синхронизируется.
  1021→  1021→- Изменение текста синхронизируется.
  1022→  1022→- Счётчик участников показывает корректное значение.
  1023→  1023→
  1024→  1024→### 18.4. Копия
  1025→  1025→
  1026→  1026→- Пользователь нажимает «Сделать копию».
  1027→  1027→- Копия появляется в списке.
  1028→  1028→- Пользователь открывает копию.
  1029→  1029→- UI показывает режим «копия».
  1030→  1030→- Изменения в копии не влияют на оригинал.
  1031→  1031→
  1032→  1032→### 18.5. Merge
  1033→  1033→
  1034→  1034→- Пользователь редактирует копию.
  1035→  1035→- Нажимает «Отправить merge».
  1036→  1036→- Владелец оригинала подключается к merge-запросам.
  1037→  1037→- Владелец видит запрос.
  1038→  1038→- Владелец видит сводку изменений.
  1039→  1039→- При нажатии «Принять» изменения появляются в оригинале.
  1040→  1040→- При нажатии «Отклонить» оригинал не меняется.
  1041→  1041→
  1042→  1042→### 18.6. Экспорт/импорт
  1043→  1043→
  1044→  1044→- Проект можно экспортировать в JSON.
  1045→  1045→- Экспортированный JSON можно импортировать обратно.
  1046→  1046→- Данные не теряются.
  1047→  1047→
  1048→  1048→### 18.7. Ошибки
  1049→  1049→
  1050→  1050→- При недоступном signaling пользователь видит ошибку.
  1051→  1051→- При ошибке IndexedDB приложение не падает полностью.
  1052→  1052→- При неудачном merge пользователь получает уведомление.
  1053→  1053→
