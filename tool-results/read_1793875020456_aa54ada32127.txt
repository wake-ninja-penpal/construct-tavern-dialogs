     1→
     2→# ТЗ: общий доступ, realtime-синхронизация, копии и merge для «Ветвей»
     3→
     4→## 1. Контекст
     5→
     6→Сейчас «Ветви» — это браузерный конструктор нарратива с локальной работой:
     7→
     8→- холст;
     9→- элементы;
    10→- инспектор;
    11→- реплики диалога;
    12→- заметки;
    13→- автосохранение;
    14→- экспорт/импорт JSON;
    15→- экспорт в текстовый файл.
    16→
    17→Нужно добавить возможность:
    18→
    19→1. дать другому человеку ссылку на проект;
    20→2. чтобы второй человек мог подключиться к проекту в realtime;
    21→3. чтобы участники могли совместно редактировать проект, пока оба онлайн;
    22→4. чтобы любой участник мог сделать копию проекта себе;
    23→5. чтобы позже изменения из копии можно было отправить владельцу оригинала;
    24→6. чтобы владелец оригинала мог просмотреть, принять или отклонить эти изменения.
    25→
    26→При этом важное ограничение:
    27→
    28→> Фронтенд должен хоститься на GitHub Pages.  
    29→> Полноценный собственный backend делать не хочется.
    30→
    31→---
    32→
    33→## 2. Цель фичи
    34→
    35→Сделать минимальный совместный режим работы над проектом «Ветви» без полноценного бэкенда, используя:
    36→
    37→- статический фронтенд на GitHub Pages;
    38→- Yjs как CRDT-модель совместного документа;
    39→- WebRTC как транспорт для realtime-обмена изменениями;
    40→- локальное хранение проекта у создателя через IndexedDB;
    41→- механизм копий и merge-запросов.
    42→
    43→---
    44→
    45→## 3. Ключевой принцип
    46→
    47→> Проект хранится у создателя, но realtime-доступ возможен только тогда, когда создатель или другой участник с актуальной копией находится онлайн.
    48→
    49→Это важно зафиксировать, потому что в модели «только GitHub Pages + WebRTC» нет постоянного сервера хранения.
    50→
    51→То есть:
    52→
    53→- если создатель онлайн — проект доступен для подключения;
    54→- если создатель офлайн, но кто-то из участников онлайн с актуальной копией — можно подключиться к нему;
    55→- если все офлайн — проект живёт только локально у тех, кто его сохранял.
    56→
    57→Для MVP это приемлемо.
    58→
    59→---
    60→
    61→## 4. Пользовательские роли
    62→
    63→### 4.1. Создатель / владелец проекта
    64→
    65→Тот, кто создал проект.
    66→
    67→Возможности:
    68→
    69→- создавать проект;
    70→- редактировать проект;
    71→- открывать realtime-комнату;
    72→- давать ссылку другим;
    73→- хранить основную версию проекта локально;
    74→- получать merge-запросы из копий;
    75→- просматривать изменения перед применением;
    76→- принимать или отклонять merge-запросы.
    77→
    78→### 4.2. Соавтор / участник
    79→
    80→Тот, кто открыл ссылку на проект.
    81→
    82→Возможности:
    83→
    84→- подключиться к realtime-комнате;
    85→- видеть текущее состояние проекта;
    86→- редактировать проект, пока подключён;
    87→- сделать копию проекта себе;
    88→- позже отправить изменения из копии владельцу оригинала.
    89→
    90→### 4.3. Редактор копии
    91→
    92→Тот, кто работает локально со своей копией.
    93→
    94→Возможности:
    95→
    96→- открыть свою копию;
    97→- редактировать её без обязательного подключения к оригиналу;
    98→- отправить merge-запрос, когда оригинал снова станет доступен.
    99→
   100→---
   101→
   102→## 5. Основные пользовательские сценарии
   103→
   104→### Сценарий 1. Создать проект и открыть доступ
   105→
   106→1. Пользователь открывает «Ветви».
   107→2. Создаёт проект.
   108→3. Добавляет элементы, реплики, заметки.
   109→4. Проект автоматически сохраняется локально.
   110→5. Пользователь нажимает «Поделиться».
   111→6. Приложение генерирует ссылку вида:
   112→
   113→```text
   114→https://username.github.io/vetvi/#room=...&project=...
   115→```
   116→
   117→7. Пользователь отправляет ссылку другому человеку.
   118→
   119→---
   120→
   121→### Сценарий 2. Подключиться по ссылке и работать вместе
   122→
   123→1. Второй пользователь открывает ссылку.
   124→2. Приложение подключается к WebRTC-комнате.
   125→3. Если создатель онлайн, второй пользователь получает текущее состояние проекта.
   126→4. Оба видят количество участников.
   127→5. Изменения одного участника появляются у другого в realtime.
   128→
   129→Пример:
   130→
   131→- создатель двигает элемент;
   132→- соавтор видит движение;
   133→- соавтор меняет текст;
   134→- создатель видит изменение текста.
   135→
   136→---
   137→
   138→### Сценарий 3. Сделать копию проекта
   139→
   140→1. Участник находится в проекте.
   141→2. Нажимает «Сделать копию».
   142→3. Приложение сохраняет локальную копию проекта.
   143→4. Запоминается:
   144→   - идентификатор копии;
   145→   - идентификатор оригинала;
   146→   - комната оригинала;
   147→   - состояние оригинала на момент копирования;
   148→   - дата создания.
   149→5. Копия появляется в списке локальных копий.
   150→
   151→---
   152→
   153→### Сценарий 4. Работать в копии офлайн
   154→
   155→1. Пользователь открывает свою копию.
   156→2. Приложение переходит в режим «копия».
   157→3. Пользователь редактирует копию локально.
   158→4. Изменения сохраняются в IndexedDB.
   159→5. Оригинал при этом может быть офлайн.
   160→
   161→---
   162→
   163→### Сценарий 5. Отправить изменения из копии в оригинал
   164→
   165→1. Пользователь находится в копии.
   166→2. Нажимает «Отправить merge».
   167→3. Приложение вычисляет разницу между копией и состоянием оригинала на момент копирования.
   168→4. Приложение подключается к служебной merge-комнате оригинала.
   169→5. Отправляет merge-запрос.
   170→6. Если владелец оригинала онлайн, он получает запрос.
   171→7. Если владелец офлайн, запрос может остаться в локальной очереди отправителя до следующей попытки.
   172→
   173→---
   174→
   175→### Сценарий 6. Принять изменения в оригинале
   176→
   177→1. Владелец оригинала открывает проект.
   178→2. Подключается к merge-комнате.
   179→3. Видит входящие merge-запросы.
   180→4. Для каждого запроса видит краткую сводку:
   181→   - кто отправил;
   182→   - когда;
   183→   - сколько элементов добавлено;
   184→   - сколько изменено;
   185→   - сколько удалено.
   186→5. Владелец может:
   187→   - принять;
   188→   - отклонить.
   189→6. При принятии изменения применяются к оригиналу.
   190→7. Перед применением создается локальный backup состояния оригинала.
   191→
   192→---
   193→
   194→## 6. Функциональные требования
   195→
   196→### FR-1. Идентификация проекта и комнаты
   197→
   198→Система должна поддерживать:
   199→
   200→- уникальный `projectId`;
   201→- уникальный `roomId` для realtime-комнаты;
   202→- ссылку формата:
   203→
   204→```text
   205→#room=...&project=...
   206→```
   207→
   208→Требования:
   209→
   210→- `projectId` не должен меняться при обычном редактировании;
   211→- `roomId` должен быть случайным и достаточно длинным, чтобы ссылку нельзя было легко угадать;
   212→- ссылка должна работать на GitHub Pages без серверных rewrite-правил;
   213→- параметры должны находиться в hash-части URL, чтобы не зависеть от маршрутизации сервера.
   214→
   215→---
   216→
   217→### FR-2. Realtime-подключение по ссылке
   218→
   219→Приложение должно:
   220→
   221→- читать `roomId` из URL;
   222→- подключаться к WebRTC-комнате;
   223→- показывать статус подключения:
   224→  - офлайн;
   225→  - подключение;
   226→  - подключено;
   227→  - ошибка;
   228→- показывать количество участников;
   229→- автоматически переподключаться при временном разрыве, насколько это возможно.
   230→
   231→Важно:
   232→
   233→> Для WebRTC нужен signaling-канал.  
   234→> В MVP допускается использовать публичный signaling-сервис.  
   235→> Для продакшена позже желательно поднять свой мини-signaling.
   236→
   237→---
   238→
   239→### FR-3. Синхронизация состояния проекта
   240→
   241→В realtime-режиме должны синхронизироваться как минимум:
   242→
   243→- элементы на холсте;
   244→- их позиция;
   245→- их размер;
   246→- их тип;
   247→- их текст;
   248→- связи между элементами, если они есть в текущей модели;
   249→- реплики диалога;
   250→- заметки;
   251→- метаинформация проекта:
   252→  - название;
   253→  - версия схемы;
   254→  - дата создания;
   255→  - дата изменения.
   256→
   257→Не обязательно в MVP синхронизировать:
   258→
   259→- локальное выделение пользователя;
   260→- состояние скролла;
   261→- zoom;
   262→- открытые модалки;
   263→- черновые состояния UI.
   264→
   265→Но можно добавить позже.
   266→
   267→---
   268→
   269→### FR-4. Локальное хранение у создателя
   270→
   271→Создатель проекта должен хранить основную версию проекта локально.
   272→
   273→Требования:
   274→
   275→- проект сохраняется в IndexedDB;
   276→- автосохранение должно продолжаться работать;
   277→- после перезагрузки страницы проект восстанавливается;
   278→- экспорт в JSON должен оставаться возможным;
   279→- импорт из JSON должен оставаться возможным.
   280→
   281→Важно:
   282→
   283→> В P2P-модели любой подключившийся участник технически получает копию документа в память браузера.  
   284→> Нельзя гарантировать, что гость не сохранит или не скопирует данные.  
   285→> Поэтому «хранение у создателя» означает каноническую локальную версию, а не абсолютную защиту от копирования.
   286→
   287→---
   288→
   289→### FR-5. Создание копии проекта
   290→
   291→Любой участник должен иметь возможность создать копию текущего проекта.
   292→
   293→Копия должна содержать:
   294→
   295→- собственный `copyId`;
   296→- снимок состояния проекта на момент копирования;
   297→- ссылку на исходный проект;
   298→- ссылку на исходную комнату;
   299→- базовое состояние оригинала для будущего merge;
   300→- дату создания.
   301→
   302→Копия должна сохраняться локально в IndexedDB.
   303→
   304→---
   305→
   306→### FR-6. Работа с копией
   307→
   308→Пользователь должен иметь возможность:
   309→
   310→- открыть список своих копий;
   311→- открыть копию;
   312→- редактировать копию локально;
   313→- видеть, что сейчас активен режим «копия», а не «оригинал»;
   314→- вернуться к оригиналу или другому проекту.
   315→
   316→---
   317→
   318→### FR-7. Вычисление изменений копии
   319→
   320→Приложение должно уметь вычислить, что именно изменилось в копии относительно момента её создания.
   321→
   322→Концептуально это означает:
   323→
   324→- есть оригинал в состоянии `A`;
   325→- из него создана копия;
   326→- копия изменена до состояния `B`;
   327→- нужно получить дельту `B - A`;
   328→- эту дельту можно применить к оригиналу.
   329→
   330→В Yjs это реализуется через механизмы состояния документа и state vector, но в ТЗ достаточно зафиксировать поведение.
   331→
   332→---
   333→
   334→### FR-8. Merge-запросы
   335→
   336→Изменения из копии не должны автоматически применяться к оригиналу.
   337→
   338→Нужен механизм merge-запросов.
   339→
   340→Merge-запрос должен содержать:
   341→
   342→- идентификатор запроса;
   343→- идентификатор отправителя;
   344→- имя или метку отправителя;
   345→- идентификатор копии;
   346→- идентификатор исходной комнаты;
   347→- дату создания;
   348→- дельту изменений;
   349→- статус:
   350→  - pending;
   351→  - applied;
   352→  - rejected.
   353→
   354→---
   355→
   356→### FR-9. Почтовый ящик оригинала
   357→
   358→Для merge-запросов нужна отдельная служебная комната, условно «mailbox».
   359→
   360→Например:
   361→
   362→- основная комната проекта: `roomId`
   363→- merge-комната: `roomId + mailbox suffix`
   364→
   365→Требования:
   366→
   367→- merge-комната не должна смешиваться с основным документом проекта;
   368→- в неё можно отправлять заявки;
   369→- владелец оригинала может подключиться к ней и получить заявки;
   370→- заявки должны быть видны только в контексте конкретного оригинала.
   371→
   372→---
   373→
   374→### FR-10. Просмотр merge-запроса владельцем
   375→
   376→Владелец оригинала должен видеть список входящих запросов.
   377→
   378→Для каждого запроса нужно показывать:
   379→
   380→- автора;
   381→- дату;
   382→- статус;
   383→- краткую статистику изменений;
   384→- кнопки «Принять» и «Отклонить».
   385→
   386→Минимальная статистика:
   387→
   388→- добавлено элементов;
   389→- изменено элементов;
   390→- удалено элементов;
   391→- изменено реплик;
   392→- изменено заметок;
   393→- изменено связей, если applicable.
   394→
   395→Для MVP достаточно сводки. Подробный visual diff можно отложить.
   396→
   397→---
   398→
   399→### FR-11. Применение merge-запроса
   400→
   401→При нажатии «Принять»:
   402→
   403→1. система создает backup текущего состояния оригинала;
   404→2. применяет дельту к оригиналу;
   405→3. помечает запрос как `applied`;
   406→4. обновляет UI;
   407→5. показывает уведомление об успехе.
   408→
   409→При нажатии «Отклонить»:
   410→
   411→1. запрос помечается как `rejected`;
   412→2. оригинал не изменяется.
   413→
   414→---
   415→
   416→### FR-12. Обработка ошибок
   417→
   418→Приложение должно показывать понятные ошибки, а не падать молча.
   419→
   420→Минимум:
   421→
   422→- не удалось подключиться к signaling;
   423→- WebRTC не запустился;
   424→- не удалось создать копию;
   425→- не удалось отправить merge-запрос;
   426→- merge-запрос не найден;
   427→- запрос не относится к текущей комнате;
   428→- ошибка чтения/записи IndexedDB;
   429→- ошибка импорта/экспорта JSON.
   430→
   431→---
   432→
   433→### FR-13. Совместимость с текущим экспортом/импортом
   434→
   435→Текущие функции должны сохраниться:
   436→
   437→- Сохранить;
   438→- Открыть;
   439→- Сохранить JSON;
   440→- Сохранить как JSON;
   441→- Текстовый файл.
   442→
   443→Новый формат проекта должен быть совместим или иметь версию схемы.
   444→
   445→Рекомендуется добавить:
   446→
   447→```text
   448→format: vetvi-project
   449→schemaVersion: 1
   450→```
   451→
   452→Если текущий JSON уже имеет другую структуру, нужен миграционный слой.
   453→
   454→---
   455→
   456→## 7. Нефункциональные требования
   457→
   458→### NF-1. Хостинг
   459→
   460→Приложение должно оставаться статическим и хоститься на GitHub Pages.
   461→
   462→Разрешено использовать:
   463→
   464→- внешние CDN для JS-библиотек;
   465→- публичные signaling-сервисы для WebRTC;
   466→- локальное хранилище браузера.
   467→
   468→Не требуется в MVP:
   469→
   470→- собственный API;
   471→- база данных на сервере;
   472→- авторизация;
   473→- серверная бизнес-логика.
   474→
   475→---
   476→
   477→### NF-2. Производительность
   478→
   479→Синхронизация не должна подвисать UI при обычном количестве элементов.
   480→
   481→Ожидаемый масштаб MVP:
   482→
   483→- десятки элементов;
   484→- сотни текстовых полей;
   485→- несколько участников одновременно.
   486→
   487→Не требуется оптимизировать под тысячи узлов и десятки пользователей сразу.
   488→
   489→---
   490→
   491→### NF-3. Надежность
   492→
   493→Нужны:
   494→
   495→- reconnect;
   496→- локальное сохранение;
   497→- backup перед merge;
   498→- очередь неотправленных merge-запросов;
   499→- graceful degradation, если WebRTC недоступен.
   500→
   501→Если realtime недоступен, пользователь должен иметь возможность:
   502→
   503→- работать локально;
   504→- экспортировать JSON;
   505→- позже импортировать или отправить merge.
   506→
   507→---
   508→
   509→### NF-4. Безопасность и приватность
   510→
   511→Для MVP:
   512→
   513→- ссылка на комнату считается секретом;
   514→- кто имеет ссылку, тот может подключиться;
   515→- данные передаются между браузерами через WebRTC;
   516→- signaling видит идентификатор комнаты, но не обязан видеть содержимое проекта;
   517→- клиентские ограничения не являются настоящей защитой от злонамеренного участника.
   518→
   519→Не входит в MVP:
   520→
   521→- серверная авторизация;
   522→- роли с криптографической проверкой;
   523→- защита от экспорта данных участником;
   524→- end-to-end шифрование с паролями.
   525→
   526→---
   527→
   528→## 8. Ограничения подхода
   529→
   530→Важно честно зафиксировать ограничения.
   531→
   532→### 8.1. GitHub Pages не может быть signaling-сервером
   533→
   534→GitHub Pages отдаёт только статику.
   535→
   536→Он не может:
   537→
   538→- принимать WebSocket-соединения;
   539→- хранить realtime-комнаты;
   540→- обрабатывать серверную логику.
   541→
   542→Поэтому для realtime нужен внешний посредник:
   543→
   544→- публичный signaling для WebRTC;
   545→- или свой мини-signaling;
   546→- или managed realtime-сервис.
   547→
   548→---
   549→
   550→### 8.2. WebRTC может не сработать в сложных сетях
   551→
   552→Без TURN-сервера часть пользователей может не соединиться.
   553→
   554→Проблемные случаи:
   555→
   556→- корпоративные файрволы;
   557→- строгие NAT;
   558→- мобильные сети;
   559→- CGNAT;
   560→- VPN;
   561→- блокировка UDP.
   562→
   563→Для MVP это допустимо.  
   564→Для продакшена нужен TURN или fallback на WebSocket relay.
   565→
   566→---
   567→
   568→### 8.3. Если владелец офлайн, проект не «живёт в облаке»
   569→
   570→В модели «данные у создателя» нет постоянного серверного хранения.
   571→
   572→Если все закрыли вкладки:
   573→
   574→- проект существует только локально у тех, кто его сохранял;
   575→- новый участник не сможет подключиться, если никто не держит комнату;
   576→- merge-запросы могут не доставляться, пока стороны снова не окажутся онлайн.
   577→
   578→---
   579→
   580→### 8.4. Полный read-only без сервера обеспечить сложно
   581→
   582→Если участник подключился к документу, он технически может изменить свою локальную копию.
   583→
   584→Можно сделать:
   585→
   586→- UI read-only;
   587→- запрет редактирования в интерфейсе.
   588→
   589→Но нельзя гарантировать, что человек с DevTools не обойдёт ограничение.
   590→
   591→Для доверенных соавторов это нормально.  
   592→Для строгой защиты нужен серверный контроль.
   593→

   632→## 10. Модель данных
   633→
   634→Нужно разделить проект на независимые структуры, чтобы удобно экспортировать, импортировать и синхронизировать.
   635→
   636→Рекомендуемые корневые коллекции:
   637→
   638→```text
   639→meta
   640→elements
   641→connections
   642→dialogues
   643→notes
   644→viewport
   645→```
   646→
   647→### 10.1. meta
   648→
   649→Хранит служебную информацию:
   650→
   651→- projectId;
   652→- name;
   653→- schemaVersion;
   654→- createdAt;
   655→- updatedAt;
   656→- createdBy;
   657→- sourceProjectId, если это копия.
   658→
   659→### 10.2. elements
   660→
   661→Элементы холста.
   662→
   663→Каждый элемент должен иметь:
   664→
   665→- стабильный уникальный id;
   666→- type;
   667→- x;
   668→- y;
   669→- width;
   670→- height;
   671→- text или другие поля;
   672→- updatedAt.
   673→
   674→### 10.3. connections
   675→
   676→Связи между элементами, если они есть.
   677→
   678→Каждая связь:
   679→
   680→- id;
   681→- from;
   682→- to;
   683→- type;
   684→- label;
   685→- updatedAt.
   686→
   687→### 10.4. dialogues
   688→
   689→Реплики диалога.
   690→
   691→Каждая реплика:
   692→
   693→- id;
   694→- speaker;
   695→- text;
   696→- order;
   697→- elementId, если привязана к элементу;
   698→- updatedAt.
   699→
   700→### 10.5. notes
   701→
   702→Заметки.
   703→
   704→Каждая заметка:
   705→
   706→- id;
   707→- title;
   708→- content;
   709→- tags;
   710→- elementId, если applicable;
   711→- updatedAt.
   712→
   713→### 10.6. viewport
   714→
   715→Необязательно для MVP, но можно хранить:
   716→
   717→- zoom;
   718→- pan;
   719→- selected element;
   720→- состояние обзора.
   721→
   722→Для realtime лучше не синхронизировать viewport агрессивно, чтобы не создавать лишнего шума.

   726→## 11. Требования к ID и конфликтам
   727→
   728→### 11.1. Уникальные ID
   729→
   730→Все сущности должны иметь стабильные уникальные ID.
   731→
   732→Нельзя:
   733→
   734→- пересоздавать ID при каждом сохранении;
   735→- использовать индекс массива как ID;
   736→- переиспользовать удалённые ID.
   737→
   738→Рекомендуется:
   739→
   740→- UUID или аналог;
   741→- ID создаётся один раз при создании сущности.
   742→
   743→### 11.2. Конфликты полей
   744→
   745→Для скалярных полей, например `x`, `y`, `width`, применяется CRDT-разрешение конфликта.
   746→
   747→Для текста лучше использовать коллаборативный текстовый тип, если нужно посимвольное слияние.
   748→
   749→Если текст хранится как обычная строка, то при одновременном изменении одного поля победит одно из значений по правилам CRDT.
   750→
   751→### 11.3. Удаление и изменение
   752→
   753→Если один участник удалил элемент, а другой его изменил, система должна предсказуемо разрешить конфликт.
   754→
   755→Для MVP достаточно положиться на Yjs.  
   756→Для более зрелой версии можно добавить tombstones и UI конфликтов.
   757→

   839→## 13. Поведение при different states
   840→
   841→### 13.1. Обычный локальный проект
   842→
   843→Пользователь работает без ссылки.
   844→
   845→- проект сохраняется в IndexedDB;
   846→- экспорт/импорт работают;
   847→- realtime не активен.
   848→
   849→### 13.2. Проект с открытой комнатой
   850→
   851→Пользователь нажал «Поделиться».
   852→
   853→- создан или использован `roomId`;
   854→- подключен WebRTC provider;
   855→- изменения синхронизируются;
   856→- проект по-прежнему сохраняется локально.
   857→
   858→### 13.3. Режим копии
   859→
   860→Пользователь открыл копию.
   861→
   862→- редактирование идёт в локальном документе копии;
   863→- оригинал не меняется;
   864→- кнопка «Поделиться» должна быть недоступна или предупреждать, что это копия;
   865→- доступна кнопка «Отправить merge».
   866→
   867→### 13.4. Ожидание владельца для merge
   868→
   869→Если владелец оригинала офлайн:
   870→
   871→- merge-запрос можно сохранить в локальной очереди;
   872→- при следующем подключении приложение пытается отправить его снова.

   876→## 14. Требования к merge
   877→
   878→### 14.1. Merge не должен быть полностью автоматическим
   879→
   880→Владелец оригинала должен подтверждать применение изменений.
   881→
   882→Причина:
   883→
   884→- даже CRDT может привести к неочевидному результату;
   885→- пользователь должен понимать, что принимает чужие правки.
   886→
   887→### 14.2. Нужен preview
   888→
   889→Минимальный preview:
   890→
   891→- сколько объектов добавлено;
   892→- сколько изменено;
   893→- сколько удалено.
   894→
   895→Желательно в будущем:
   896→
   897→- список изменённых элементов;
   898→- подсветка на холсте;
   899→- режим «посмотреть до применения».
   900→
   901→### 14.3. Нужен backup
   902→
   903→Перед применением merge нужно сохранить snapshot оригинала.
   904→
   905→Это позволит откатить состояние, если изменения оказались нежелательными.

   910→
   911→### 15.1. MVP
   912→
   913→Для проверки гипотезы можно использовать публичный signaling.
   914→
   915→Ожидаемое поведение:
   916→
   917→- приложение загружается с GitHub Pages;
   918→- пользователь получает ссылку;
   919→- второй пользователь открывается по ссылке;
   920→- браузеры соединяются через WebRTC.
   921→
   922→### 15.2. Продакшен-вариант
   923→
   924→Для стабильности позже нужен свой мини-signaling.
   925→
   926→Это не полноценный backend, а сервис рукопожатий.
   927→
   928→Он может быть размещён, например:
   929→
   930→- Cloudflare Workers / Durable Objects;
   931→- PartyKit;
   932→- маленький Node.js сервис;
   933→- Fly.io;
   934→- Render;
   935→- Railway.
   936→
   937→### 15.3. TURN
   938→
   939→Для надёжного соединения в реальных сетях желателен TURN.
   940→
   941→Без TURN часть пользователей не подключится.

   999→## 18. Критерии приёмки MVP
  1000→
  1001→### 18.1. Локальный проект
  1002→
  1003→- Пользователь создаёт проект.
  1004→- Добавляет элемент.
  1005→- Перезагружает страницу.
  1006→- Проект восстановлен.
  1007→
  1008→### 18.2. Поделиться
  1009→
  1010→- Пользователь нажимает «Поделиться».
  1011→- В URL появляются `room` и `project`.
  1012→- Ссылка копируется.
  1013→- Статус меняется на «подключение» или «подключено».
  1014→
  1015→### 18.3. Realtime
  1016→
  1017→- Второй браузер открывает ссылку.
  1018→- Оба пользователя видят один проект.
  1019→- Изменение элемента в одном браузере появляется в другом.
  1020→- Перемещение элемента синхронизируется.
  1021→- Изменение текста синхронизируется.
  1022→- Счётчик участников показывает корректное значение.
  1023→
  1024→### 18.4. Копия
  1025→
  1026→- Пользователь нажимает «Сделать копию».
  1027→- Копия появляется в списке.
  1028→- Пользователь открывает копию.
  1029→- UI показывает режим «копия».
  1030→- Изменения в копии не влияют на оригинал.
  1031→
  1032→### 18.5. Merge
  1033→
  1034→- Пользователь редактирует копию.
  1035→- Нажимает «Отправить merge».
  1036→- Владелец оригинала подключается к merge-запросам.
  1037→- Владелец видит запрос.
  1038→- Владелец видит сводку изменений.
  1039→- При нажатии «Принять» изменения появляются в оригинале.
  1040→- При нажатии «Отклонить» оригинал не меняется.
  1041→
  1042→### 18.6. Экспорт/импорт
  1043→
  1044→- Проект можно экспортировать в JSON.
  1045→- Экспортированный JSON можно импортировать обратно.
  1046→- Данные не теряются.
  1047→
  1048→### 18.7. Ошибки
  1049→
  1050→- При недоступном signaling пользователь видит ошибку.
  1051→- При ошибке IndexedDB приложение не падает полностью.
  1052→- При неудачном merge пользователь получает уведомление.
  1053→

  1472→## 20. Риски и меры снижения
  1473→
  1474→### Риск 1. Публичный signaling нестабилен
  1475→
  1476→Симптомы:
  1477→
  1478→- ссылки не работают;
  1479→- участники не подключаются;
  1480→- соединение часто рвётся.
  1481→
  1482→Митигация:
  1483→
  1484→- использовать несколько signaling endpoints;
  1485→- показать понятную ошибку;
  1486→- позже поднять свой мини-signaling.
  1487→
  1488→---
  1489→
  1490→### Риск 2. WebRTC не проходит NAT/firewall
  1491→
  1492→Симптомы:
  1493→
  1494→- у одного пользователя подключено, у другого нет;
  1495→- статус зависает на «подключение».
  1496→
  1497→Митигация:
  1498→
  1499→- добавить STUN;
  1500→- для продакшена добавить TURN;
  1501→- сделать fallback на экспорт/импорт JSON.
  1502→
  1503→---
  1504→
  1505→### Риск 3. Владелец закрыл вкладку, проект недоступен
  1506→
  1507→Симптомы:
  1508→
  1509→- по ссылке никто не подключается;
  1510→- merge-запросы не доставляются.
  1511→
  1512→Митигация:
  1513→
  1514→- локальная очередь merge-запросов;
  1515→- периодический экспорт snapshot;
  1516→- в будущем — постоянное хранилище снапшотов.
  1517→
  1518→---
  1519→
  1520→### Риск 4. Текущее приложение не имеет единого state
  1521→
  1522→Симптомы:
  1523→
  1524→- данные разбросаны по DOM;

  1528→
  1529→- этап 1: выделить adapter/state слой до интеграции Yjs.
  1530→
  1531→---
  1532→
  1533→### Риск 5. Конфликты текста будут выглядеть странно

  1537→- два пользователя редактируют одно поле;

  1540→Митигация:
  1541→
  1542→- использовать коллаборативный текстовый тип;

  1733→## 25. Итоговое резюме
  1734→
  1735→Фичу можно реализовать в такой конфигурации:
  1736→
  1737→```text
  1738→GitHub Pages
  1739→+ Yjs
  1740→+ y-webrtc
  1741→+ публичный signaling для MVP
  1742→+ IndexedDB у создателя
  1743→+ копии
  1744→+ merge через delta updates
  1745→```
  1746→
  1747→Полноценный backend не обязателен для прототипа, но нужно принять ограничения:
  1748→
  1749→- signaling всё равно нужен;
  1750→- WebRTC может не работать в сложных сетях без TURN;
  1751→- проект доступен realtime только когда кто-то с актуальной копией онлайн;
  1752→- клиентский read-only не является настоящей защитой;
  1753→- merge должен быть ручным и с backup.
  1754→
  1755→Самый разумный MVP:
  1756→
  1757→1. Сначала сделать, чтобы ссылка открывала общий realtime-проект.
  1758→2. Потом добавить копии.
  1759→3. Потом добавить merge-запросы.
  1760→4. Уже после этого решать, нужен ли свой signaling и TURN.
