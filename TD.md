
# ТЗ: общий доступ, realtime-синхронизация, копии и merge для «Ветвей»

## 1. Контекст

Сейчас «Ветви» — это браузерный конструктор нарратива с локальной работой:

- холст;
- элементы;
- инспектор;
- реплики диалога;
- заметки;
- автосохранение;
- экспорт/импорт JSON;
- экспорт в текстовый файл.

Нужно добавить возможность:

1. дать другому человеку ссылку на проект;
2. чтобы второй человек мог подключиться к проекту в realtime;
3. чтобы участники могли совместно редактировать проект, пока оба онлайн;
4. чтобы любой участник мог сделать копию проекта себе;
5. чтобы позже изменения из копии можно было отправить владельцу оригинала;
6. чтобы владелец оригинала мог просмотреть, принять или отклонить эти изменения.

При этом важное ограничение:

> Фронтенд должен хоститься на GitHub Pages.  
> Полноценный собственный backend делать не хочется.

---

## 2. Цель фичи

Сделать минимальный совместный режим работы над проектом «Ветви» без полноценного бэкенда, используя:

- статический фронтенд на GitHub Pages;
- Yjs как CRDT-модель совместного документа;
- WebRTC как транспорт для realtime-обмена изменениями;
- локальное хранение проекта у создателя через IndexedDB;
- механизм копий и merge-запросов.

---

## 3. Ключевой принцип

> Проект хранится у создателя, но realtime-доступ возможен только тогда, когда создатель или другой участник с актуальной копией находится онлайн.

Это важно зафиксировать, потому что в модели «только GitHub Pages + WebRTC» нет постоянного сервера хранения.

То есть:

- если создатель онлайн — проект доступен для подключения;
- если создатель офлайн, но кто-то из участников онлайн с актуальной копией — можно подключиться к нему;
- если все офлайн — проект живёт только локально у тех, кто его сохранял.

Для MVP это приемлемо.

---

## 4. Пользовательские роли

### 4.1. Создатель / владелец проекта

Тот, кто создал проект.

Возможности:

- создавать проект;
- редактировать проект;
- открывать realtime-комнату;
- давать ссылку другим;
- хранить основную версию проекта локально;
- получать merge-запросы из копий;
- просматривать изменения перед применением;
- принимать или отклонять merge-запросы.

### 4.2. Соавтор / участник

Тот, кто открыл ссылку на проект.

Возможности:

- подключиться к realtime-комнате;
- видеть текущее состояние проекта;
- редактировать проект, пока подключён;
- сделать копию проекта себе;
- позже отправить изменения из копии владельцу оригинала.

### 4.3. Редактор копии

Тот, кто работает локально со своей копией.

Возможности:

- открыть свою копию;
- редактировать её без обязательного подключения к оригиналу;
- отправить merge-запрос, когда оригинал снова станет доступен.

---

## 5. Основные пользовательские сценарии

### Сценарий 1. Создать проект и открыть доступ

1. Пользователь открывает «Ветви».
2. Создаёт проект.
3. Добавляет элементы, реплики, заметки.
4. Проект автоматически сохраняется локально.
5. Пользователь нажимает «Поделиться».
6. Приложение генерирует ссылку вида:

```text
https://username.github.io/vetvi/#room=...&project=...
```

7. Пользователь отправляет ссылку другому человеку.

---

### Сценарий 2. Подключиться по ссылке и работать вместе

1. Второй пользователь открывает ссылку.
2. Приложение подключается к WebRTC-комнате.
3. Если создатель онлайн, второй пользователь получает текущее состояние проекта.
4. Оба видят количество участников.
5. Изменения одного участника появляются у другого в realtime.

Пример:

- создатель двигает элемент;
- соавтор видит движение;
- соавтор меняет текст;
- создатель видит изменение текста.

---

### Сценарий 3. Сделать копию проекта

1. Участник находится в проекте.
2. Нажимает «Сделать копию».
3. Приложение сохраняет локальную копию проекта.
4. Запоминается:
   - идентификатор копии;
   - идентификатор оригинала;
   - комната оригинала;
   - состояние оригинала на момент копирования;
   - дата создания.
5. Копия появляется в списке локальных копий.

---

### Сценарий 4. Работать в копии офлайн

1. Пользователь открывает свою копию.
2. Приложение переходит в режим «копия».
3. Пользователь редактирует копию локально.
4. Изменения сохраняются в IndexedDB.
5. Оригинал при этом может быть офлайн.

---

### Сценарий 5. Отправить изменения из копии в оригинал

1. Пользователь находится в копии.
2. Нажимает «Отправить merge».
3. Приложение вычисляет разницу между копией и состоянием оригинала на момент копирования.
4. Приложение подключается к служебной merge-комнате оригинала.
5. Отправляет merge-запрос.
6. Если владелец оригинала онлайн, он получает запрос.
7. Если владелец офлайн, запрос может остаться в локальной очереди отправителя до следующей попытки.

---

### Сценарий 6. Принять изменения в оригинале

1. Владелец оригинала открывает проект.
2. Подключается к merge-комнате.
3. Видит входящие merge-запросы.
4. Для каждого запроса видит краткую сводку:
   - кто отправил;
   - когда;
   - сколько элементов добавлено;
   - сколько изменено;
   - сколько удалено.
5. Владелец может:
   - принять;
   - отклонить.
6. При принятии изменения применяются к оригиналу.
7. Перед применением создается локальный backup состояния оригинала.

---

## 6. Функциональные требования

### FR-1. Идентификация проекта и комнаты

Система должна поддерживать:

- уникальный `projectId`;
- уникальный `roomId` для realtime-комнаты;
- ссылку формата:

```text
#room=...&project=...
```

Требования:

- `projectId` не должен меняться при обычном редактировании;
- `roomId` должен быть случайным и достаточно длинным, чтобы ссылку нельзя было легко угадать;
- ссылка должна работать на GitHub Pages без серверных rewrite-правил;
- параметры должны находиться в hash-части URL, чтобы не зависеть от маршрутизации сервера.

---

### FR-2. Realtime-подключение по ссылке

Приложение должно:

- читать `roomId` из URL;
- подключаться к WebRTC-комнате;
- показывать статус подключения:
  - офлайн;
  - подключение;
  - подключено;
  - ошибка;
- показывать количество участников;
- автоматически переподключаться при временном разрыве, насколько это возможно.

Важно:

> Для WebRTC нужен signaling-канал.  
> В MVP допускается использовать публичный signaling-сервис.  
> Для продакшена позже желательно поднять свой мини-signaling.

---

### FR-3. Синхронизация состояния проекта

В realtime-режиме должны синхронизироваться как минимум:

- элементы на холсте;
- их позиция;
- их размер;
- их тип;
- их текст;
- связи между элементами, если они есть в текущей модели;
- реплики диалога;
- заметки;
- метаинформация проекта:
  - название;
  - версия схемы;
  - дата создания;
  - дата изменения.

Не обязательно в MVP синхронизировать:

- локальное выделение пользователя;
- состояние скролла;
- zoom;
- открытые модалки;
- черновые состояния UI.

Но можно добавить позже.

---

### FR-4. Локальное хранение у создателя

Создатель проекта должен хранить основную версию проекта локально.

Требования:

- проект сохраняется в IndexedDB;
- автосохранение должно продолжаться работать;
- после перезагрузки страницы проект восстанавливается;
- экспорт в JSON должен оставаться возможным;
- импорт из JSON должен оставаться возможным.

Важно:

> В P2P-модели любой подключившийся участник технически получает копию документа в память браузера.  
> Нельзя гарантировать, что гость не сохранит или не скопирует данные.  
> Поэтому «хранение у создателя» означает каноническую локальную версию, а не абсолютную защиту от копирования.

---

### FR-5. Создание копии проекта

Любой участник должен иметь возможность создать копию текущего проекта.

Копия должна содержать:

- собственный `copyId`;
- снимок состояния проекта на момент копирования;
- ссылку на исходный проект;
- ссылку на исходную комнату;
- базовое состояние оригинала для будущего merge;
- дату создания.

Копия должна сохраняться локально в IndexedDB.

---

### FR-6. Работа с копией

Пользователь должен иметь возможность:

- открыть список своих копий;
- открыть копию;
- редактировать копию локально;
- видеть, что сейчас активен режим «копия», а не «оригинал»;
- вернуться к оригиналу или другому проекту.

---

### FR-7. Вычисление изменений копии

Приложение должно уметь вычислить, что именно изменилось в копии относительно момента её создания.

Концептуально это означает:

- есть оригинал в состоянии `A`;
- из него создана копия;
- копия изменена до состояния `B`;
- нужно получить дельту `B - A`;
- эту дельту можно применить к оригиналу.

В Yjs это реализуется через механизмы состояния документа и state vector, но в ТЗ достаточно зафиксировать поведение.

---

### FR-8. Merge-запросы

Изменения из копии не должны автоматически применяться к оригиналу.

Нужен механизм merge-запросов.

Merge-запрос должен содержать:

- идентификатор запроса;
- идентификатор отправителя;
- имя или метку отправителя;
- идентификатор копии;
- идентификатор исходной комнаты;
- дату создания;
- дельту изменений;
- статус:
  - pending;
  - applied;
  - rejected.

---

### FR-9. Почтовый ящик оригинала

Для merge-запросов нужна отдельная служебная комната, условно «mailbox».

Например:

- основная комната проекта: `roomId`
- merge-комната: `roomId + mailbox suffix`

Требования:

- merge-комната не должна смешиваться с основным документом проекта;
- в неё можно отправлять заявки;
- владелец оригинала может подключиться к ней и получить заявки;
- заявки должны быть видны только в контексте конкретного оригинала.

---

### FR-10. Просмотр merge-запроса владельцем

Владелец оригинала должен видеть список входящих запросов.

Для каждого запроса нужно показывать:

- автора;
- дату;
- статус;
- краткую статистику изменений;
- кнопки «Принять» и «Отклонить».

Минимальная статистика:

- добавлено элементов;
- изменено элементов;
- удалено элементов;
- изменено реплик;
- изменено заметок;
- изменено связей, если applicable.

Для MVP достаточно сводки. Подробный visual diff можно отложить.

---

### FR-11. Применение merge-запроса

При нажатии «Принять»:

1. система создает backup текущего состояния оригинала;
2. применяет дельту к оригиналу;
3. помечает запрос как `applied`;
4. обновляет UI;
5. показывает уведомление об успехе.

При нажатии «Отклонить»:

1. запрос помечается как `rejected`;
2. оригинал не изменяется.

---

### FR-12. Обработка ошибок

Приложение должно показывать понятные ошибки, а не падать молча.

Минимум:

- не удалось подключиться к signaling;
- WebRTC не запустился;
- не удалось создать копию;
- не удалось отправить merge-запрос;
- merge-запрос не найден;
- запрос не относится к текущей комнате;
- ошибка чтения/записи IndexedDB;
- ошибка импорта/экспорта JSON.

---

### FR-13. Совместимость с текущим экспортом/импортом

Текущие функции должны сохраниться:

- Сохранить;
- Открыть;
- Сохранить JSON;
- Сохранить как JSON;
- Текстовый файл.

Новый формат проекта должен быть совместим или иметь версию схемы.

Рекомендуется добавить:

```text
format: vetvi-project
schemaVersion: 1
```

Если текущий JSON уже имеет другую структуру, нужен миграционный слой.

---

## 7. Нефункциональные требования

### NF-1. Хостинг

Приложение должно оставаться статическим и хоститься на GitHub Pages.

Разрешено использовать:

- внешние CDN для JS-библиотек;
- публичные signaling-сервисы для WebRTC;
- локальное хранилище браузера.

Не требуется в MVP:

- собственный API;
- база данных на сервере;
- авторизация;
- серверная бизнес-логика.

---

### NF-2. Производительность

Синхронизация не должна подвисать UI при обычном количестве элементов.

Ожидаемый масштаб MVP:

- десятки элементов;
- сотни текстовых полей;
- несколько участников одновременно.

Не требуется оптимизировать под тысячи узлов и десятки пользователей сразу.

---

### NF-3. Надежность

Нужны:

- reconnect;
- локальное сохранение;
- backup перед merge;
- очередь неотправленных merge-запросов;
- graceful degradation, если WebRTC недоступен.

Если realtime недоступен, пользователь должен иметь возможность:

- работать локально;
- экспортировать JSON;
- позже импортировать или отправить merge.

---

### NF-4. Безопасность и приватность

Для MVP:

- ссылка на комнату считается секретом;
- кто имеет ссылку, тот может подключиться;
- данные передаются между браузерами через WebRTC;
- signaling видит идентификатор комнаты, но не обязан видеть содержимое проекта;
- клиентские ограничения не являются настоящей защитой от злонамеренного участника.

Не входит в MVP:

- серверная авторизация;
- роли с криптографической проверкой;
- защита от экспорта данных участником;
- end-to-end шифрование с паролями.

---

## 8. Ограничения подхода

Важно честно зафиксировать ограничения.

### 8.1. GitHub Pages не может быть signaling-сервером

GitHub Pages отдаёт только статику.

Он не может:

- принимать WebSocket-соединения;
- хранить realtime-комнаты;
- обрабатывать серверную логику.

Поэтому для realtime нужен внешний посредник:

- публичный signaling для WebRTC;
- или свой мини-signaling;
- или managed realtime-сервис.

---

### 8.2. WebRTC может не сработать в сложных сетях

Без TURN-сервера часть пользователей может не соединиться.

Проблемные случаи:

- корпоративные файрволы;
- строгие NAT;
- мобильные сети;
- CGNAT;
- VPN;
- блокировка UDP.

Для MVP это допустимо.  
Для продакшена нужен TURN или fallback на WebSocket relay.

---

### 8.3. Если владелец офлайн, проект не «живёт в облаке»

В модели «данные у создателя» нет постоянного серверного хранения.

Если все закрыли вкладки:

- проект существует только локально у тех, кто его сохранял;
- новый участник не сможет подключиться, если никто не держит комнату;
- merge-запросы могут не доставляться, пока стороны снова не окажутся онлайн.

---

### 8.4. Полный read-only без сервера обеспечить сложно

Если участник подключился к документу, он технически может изменить свою локальную копию.

Можно сделать:

- UI read-only;
- запрет редактирования в интерфейсе.

Но нельзя гарантировать, что человек с DevTools не обойдёт ограничение.

Для доверенных соавторов это нормально.  
Для строгой защиты нужен серверный контроль.

---

## 9. Архитектурная концепция

Предлагаемая архитектура без полноценного бэкенда:

```text
GitHub Pages
   |
   |-- статический фронтенд «Ветвей»
   |
   |-- Yjs-документ проекта
   |
   |-- y-webrtc для realtime-синхронизации
   |
   |-- публичный signaling server для установки WebRTC-соединений
   |
   |-- IndexedDB для локального хранения
   |
   |-- отдельный mailbox-документ для merge-запросов
```

Логические слои:

```text
UI приложения
   |
Adapter layer
   |
Yjs document
   |
WebRTC transport
   |
IndexedDB persistence
```

## 10. Модель данных

Нужно разделить проект на независимые структуры, чтобы удобно экспортировать, импортировать и синхронизировать.

Рекомендуемые корневые коллекции:

```text
meta
elements
connections
dialogues
notes
viewport
```

### 10.1. meta

Хранит служебную информацию:

- projectId;
- name;
- schemaVersion;
- createdAt;
- updatedAt;
- createdBy;
- sourceProjectId, если это копия.

### 10.2. elements

Элементы холста.

Каждый элемент должен иметь:

- стабильный уникальный id;
- type;
- x;
- y;
- width;
- height;
- text или другие поля;
- updatedAt.

### 10.3. connections

Связи между элементами, если они есть.

Каждая связь:

- id;
- from;
- to;
- type;
- label;
- updatedAt.

### 10.4. dialogues

Реплики диалога.

Каждая реплика:

- id;
- speaker;
- text;
- order;
- elementId, если привязана к элементу;
- updatedAt.

### 10.5. notes

Заметки.

Каждая заметка:

- id;
- title;
- content;
- tags;
- elementId, если applicable;
- updatedAt.

### 10.6. viewport

Необязательно для MVP, но можно хранить:

- zoom;
- pan;
- selected element;
- состояние обзора.

Для realtime лучше не синхронизировать viewport агрессивно, чтобы не создавать лишнего шума.

## 11. Требования к ID и конфликтам

### 11.1. Уникальные ID

Все сущности должны иметь стабильные уникальные ID.

Нельзя:

- пересоздавать ID при каждом сохранении;
- использовать индекс массива как ID;
- переиспользовать удалённые ID.

Рекомендуется:

- UUID или аналог;
- ID создаётся один раз при создании сущности.

### 11.2. Конфликты полей

Для скалярных полей, например `x`, `y`, `width`, применяется CRDT-разрешение конфликта.

Для текста лучше использовать коллаборативный текстовый тип, если нужно посимвольное слияние.

Если текст хранится как обычная строка, то при одновременном изменении одного поля победит одно из значений по правилам CRDT.

### 11.3. Удаление и изменение

Если один участник удалил элемент, а другой его изменил, система должна предсказуемо разрешить конфликт.

Для MVP достаточно положиться на Yjs.  
Для более зрелой версии можно добавить tombstones и UI конфликтов.

## 13. Поведение при different states

### 13.1. Обычный локальный проект

Пользователь работает без ссылки.

- проект сохраняется в IndexedDB;
- экспорт/импорт работают;
- realtime не активен.

### 13.2. Проект с открытой комнатой

Пользователь нажал «Поделиться».

- создан или использован `roomId`;
- подключен WebRTC provider;
- изменения синхронизируются;
- проект по-прежнему сохраняется локально.

### 13.3. Режим копии

Пользователь открыл копию.

- редактирование идёт в локальном документе копии;
- оригинал не меняется;
- кнопка «Поделиться» должна быть недоступна или предупреждать, что это копия;
- доступна кнопка «Отправить merge».

### 13.4. Ожидание владельца для merge

Если владелец оригинала офлайн:

- merge-запрос можно сохранить в локальной очереди;
- при следующем подключении приложение пытается отправить его снова.

## 14. Требования к merge

### 14.1. Merge не должен быть полностью автоматическим

Владелец оригинала должен подтверждать применение изменений.

Причина:

- даже CRDT может привести к неочевидному результату;
- пользователь должен понимать, что принимает чужие правки.

### 14.2. Нужен preview

Минимальный preview:

- сколько объектов добавлено;
- сколько изменено;
- сколько удалено.

Желательно в будущем:

- список изменённых элементов;
- подсветка на холсте;
- режим «посмотреть до применения».

### 14.3. Нужен backup

Перед применением merge нужно сохранить snapshot оригинала.

Это позволит откатить состояние, если изменения оказались нежелательными.

---

## 15. Требования к signaling

### 15.1. MVP

Для проверки гипотезы можно использовать публичный signaling.

Ожидаемое поведение:

- приложение загружается с GitHub Pages;
- пользователь получает ссылку;
- второй пользователь открывается по ссылке;
- браузеры соединяются через WebRTC.

### 15.2. Продакшен-вариант

Для стабильности позже нужен свой мини-signaling.

Это не полноценный backend, а сервис рукопожатий.

Он может быть размещён, например:

- Cloudflare Workers / Durable Objects;
- PartyKit;
- маленький Node.js сервис;
- Fly.io;
- Render;
- Railway.

### 15.3. TURN

Для надёжного соединения в реальных сетях желателен TURN.

Без TURN часть пользователей не подключится.

## 18. Критерии приёмки MVP

### 18.1. Локальный проект

- Пользователь создаёт проект.
- Добавляет элемент.
- Перезагружает страницу.
- Проект восстановлен.

### 18.2. Поделиться

- Пользователь нажимает «Поделиться».
- В URL появляются `room` и `project`.
- Ссылка копируется.
- Статус меняется на «подключение» или «подключено».

### 18.3. Realtime

- Второй браузер открывает ссылку.
- Оба пользователя видят один проект.
- Изменение элемента в одном браузере появляется в другом.
- Перемещение элемента синхронизируется.
- Изменение текста синхронизируется.
- Счётчик участников показывает корректное значение.

### 18.4. Копия

- Пользователь нажимает «Сделать копию».
- Копия появляется в списке.
- Пользователь открывает копию.
- UI показывает режим «копия».
- Изменения в копии не влияют на оригинал.

### 18.5. Merge

- Пользователь редактирует копию.
- Нажимает «Отправить merge».
- Владелец оригинала подключается к merge-запросам.
- Владелец видит запрос.
- Владелец видит сводку изменений.
- При нажатии «Принять» изменения появляются в оригинале.
- При нажатии «Отклонить» оригинал не меняется.

### 18.6. Экспорт/импорт

- Проект можно экспортировать в JSON.
- Экспортированный JSON можно импортировать обратно.
- Данные не теряются.

### 18.7. Ошибки

- При недоступном signaling пользователь видит ошибку.
- При ошибке IndexedDB приложение не падает полностью.
- При неудачном merge пользователь получает уведомление.

## 20. Риски и меры снижения

### Риск 1. Публичный signaling нестабилен

Симптомы:

- ссылки не работают;
- участники не подключаются;
- соединение часто рвётся.

Митигация:

- использовать несколько signaling endpoints;
- показать понятную ошибку;
- позже поднять свой мини-signaling.

---

### Риск 2. WebRTC не проходит NAT/firewall

Симптомы:

- у одного пользователя подключено, у другого нет;
- статус зависает на «подключение».

Митигация:

- добавить STUN;
- для продакшена добавить TURN;
- сделать fallback на экспорт/импорт JSON.

---

### Риск 3. Владелец закрыл вкладку, проект недоступен

Симптомы:

- по ссылке никто не подключается;
- merge-запросы не доставляются.

Митигация:

- локальная очередь merge-запросов;
- периодический экспорт snapshot;
- в будущем — постоянное хранилище снапшотов.

---

### Риск 4. Текущее приложение не имеет единого state

Симптомы:

- данные разбросаны по DOM;
- сложно синхронизировать изменения.

Митигация:

- этап 1: выделить adapter/state слой до интеграции Yjs.

---

### Риск 5. Конфликты текста будут выглядеть странно

Симптомы:

- два пользователя редактируют одно поле;
- получается нечитаемый текст.

Митигация:

- использовать коллаборативный текстовый тип;
- или ограничить одновременное редактирование одного поля;
- или показывать preview/conflict UI.

---

### Риск 6. Merge применит нежелательные изменения

Симптомы:

- владелец принял запрос, но результат неожиданный.

Митигация:

- backup перед merge;
- сводка изменений;
- позже — подробный diff;
- откат через backup.

---

### Риск 7. GitHub Pages + CDN могут быть недоступны в некоторых сетях

Симптомы:

- библиотека не грузится;
- белый экран.

Митигация:

- собрать статический бандл и заливать его на GitHub Pages;
- не зависеть от runtime CDN для продакшена.

## 21. Открытые вопросы перед реализацией

Эти вопросы нужно решить до кода.

### 1. Какие сущности обязательно синхронизировать в MVP?

Вариант:

- элементы;
- связи;
- реплики;
- заметки;
- мета проекта.

Нужно уточнить, есть ли у вас отдельные сущности, которые обязательно должны попадать в realtime.

---

### 2. Нужно ли синхронизировать выделение и курсоры?

Для MVP можно нет.  
Для хорошего collaborative UX — желательно позже.

---

### 3. Все подключившиеся могут редактировать?

Для MVP предлагаю: да.

Строгий read-only без сервера надежной не сделать.

---

### 4. Merge всегда ручной?

Рекомендую: да, в MVP.

Автоматический merge опасен.

---

### 5. Нужен ли подробный diff перед merge?

Для MVP достаточно сводки.  
Подробный diff — второй этап.

---

### 6. Что делать, если оригинал офлайн во время отправки merge?

Рекомендация:

- сохранить запрос локально;
- повторять отправку при подключении.

---

### 7. Хранить ли viewport в общем документе?

Рекомендация:

- хранить локально или синхронизировать опционально;
- не делать viewport источником конфликтов в MVP.

---

### 8. Нужна ли миграция старого JSON?

Если у вас уже есть сохранённые проекты, да.

Нужно решить:

- старый формат поддерживается;
- или есть кнопка миграции;
- или старые файлы считаются legacy.

## 22. Минимальный MVP

Чтобы не раздувать первую версию, MVP должен включать только:

1. Yjs-модель проекта.
2. Локальное сохранение в IndexedDB.
3. Экспорт/импорт JSON через Yjs-модель.
4. Кнопку «Поделиться».
5. WebRTC-комнату через публичный signaling.
6. Синхронизацию элементов и текста.
7. Статус подключения и участников.
8. Кнопку «Сделать копию».
9. Список копий.
10. Открытие копии.
11. Отправку merge-запроса.
12. Просмотр merge-запросов владельцем.
13. Принятие/отклонение merge.
14. Backup перед merge.

Не входит в MVP:

- авторизация;
- роли;
- серверное хранение;
- подробный visual diff;
- курсоры;
- комментарии;
- история версий;
- TURN;
- свой signaling;
- шифрование;
- мобильная оптимизация;
- большая производительность.

Перед началом реализации нужно иметь:

## 25. Итоговое резюме

Фичу можно реализовать в такой конфигурации:

```text
GitHub Pages
+ Yjs
+ y-webrtc
+ публичный signaling для MVP
+ IndexedDB у создателя
+ копии
+ merge через delta updates
```

Полноценный backend не обязателен для прототипа, но нужно принять ограничения:

- signaling всё равно нужен;
- WebRTC может не работать в сложных сетях без TURN;
- проект доступен realtime только когда кто-то с актуальной копией онлайн;
- клиентский read-only не является настоящей защитой;
- merge должен быть ручным и с backup.

Самый разумный MVP:

1. Сначала сделать, чтобы ссылка открывала общий realtime-проект.
2. Потом добавить копии.
3. Потом добавить merge-запросы.
4. Уже после этого решать, нужен ли свой signaling и TURN.
